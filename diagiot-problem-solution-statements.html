Problem Statement

Silent Degradation in Embedded IoT Fleets

Context

Embedded IoT devices deployed in industrial, infrastructure, automotive, and logistics environments degrade silently over time. A sensor's analog readings drift away from calibrated values. A firmware update subtly alters hardware timing. A power rail develops ripple that couples noise into an ADC sampling channel. These degradation patterns are slow-moving, cross-domain, and invisible to conventional threshold-based monitors — yet they cause cascading failures in the field: incorrect actuator commands, missed safety triggers, corrupted telemetry streams, and eventual device failure.

Core tension: The smaller and more constrained the embedded device, the harder it is to instrument. Firmware updates that look identical at the functional test level can carry material drift risk that only manifests under real field conditions — temperature cycling, supply variation, long-duration timer accumulation — often weeks after deployment.

Three Compounding Challenges

  • 1
    No pre-ship firmware drift gate
    Firmware is compiled, tested at the functional level, and pushed directly to production devices without any automated scoring of how much it deviates from a known-good behavioral baseline. A release that introduces a register timing change, a DMA buffer reconfiguration, or an ADC sensitivity shift may pass all integration tests yet carry significant latent drift risk — risk that only materialises in the field, at scale, and often across hundreds of devices simultaneously.
  • 2
    Reactive, manual field diagnosis
    When a device begins drifting in production, there is no automated system to detect the anomaly early, correlate cross-signal patterns (e.g., power ripple causing ADC offset causing clock cascade), or form a root-cause hypothesis. Engineers must manually pull telemetry logs, mentally compare against remembered baselines, and trace through recent firmware changelogs — a process that takes hours to days per incident and requires deep institutional knowledge that is rarely documented or transferable.
  • 3
    Knowledge loss and slow engineer onboarding
    When experienced engineers resolve a drift incident, findings and resolution steps are rarely captured in a structured, searchable form. New engineers have no guided path into the platform, device families, or diagnostic workflows — resulting in repeated investigative effort across incidents, long time-to-resolution for recurring failure modes, and a months-long ramp for new team members before they can investigate independently.

Business and Operational Impact

Firmware carrying drift risk ships undetected and reaches production devices
Drift-related field incidents are detected late, after measurable degradation
Institutional diagnostic knowledge lives in individuals, not the organisation
New engineers require weeks of shadowing before independent incident response

Solution Statement

DiagIoT — Three-Agent Agentic Drift Detection Platform

The Three Agents

AgentPhaseCore Function
Pre-Ship Agent Pre-deployment Scans every firmware build, computes a weighted 5-component drift-risk score, and issues a Pass / Warn / Block gate decision before any release reaches a device. Integrates directly into Arduino, VS Code, Keil, Jenkins, GitHub Actions, and Docker pipelines.
Monitor & Investigate Agent In-field Continuously evaluates incoming device telemetry against captured golden baselines, detects threshold crossings with debounced alerting, correlates cross-signal patterns across a 6-signal dimension space, and publishes typed, confidence-scored root-cause hypotheses.
Onboarding Agent Human enablement Guides new engineers through a staged learning path covering platform architecture, hardware setup, drift workflows, and CI/CD gating. Curates institutional knowledge from resolved incidents into a structured, searchable Knowledge Base accessible across all future investigations.

The Drift Score — A Unified Decision Metric

Every decision in the platform is driven by a single normalised 0.00–1.00 drift score, computed with different input weights for firmware risk (pre-ship) versus field telemetry health (monitoring). A consistent scale means the same thresholds, the same verdict vocabulary, and the same alert severity model apply across both pipelines.

Platform Capabilities

  • Pre-Ship Scanning & CI/CD Gate Hooks into Arduino IDE, VS Code/PlatformIO, Keil/STM32CubeIDE, Jenkins CI, GitHub Actions, and Docker builds. Scores each firmware release on five dimensions and issues a Pass / Warn / Block verdict that can gate the entire deployment pipeline automatically.
  • Fleet Health Dashboard Real-time view of all registered devices across fleets — per-device drift scores, health status (Healthy / Warning / Critical), live alert feed, and trend charts delivered via WebSocket push. No polling required.
  • Field Monitor & Alert System Evaluates every incoming telemetry sample against the device's captured golden baseline. Detects threshold crossings with debounced alerting (no alert storms), raises typed alerts with signal-level detail, and supports in-platform acknowledgement with attribution.
  • Drift Analysis & Cross-Signal Correlation A 6×6 signal correlation heatmap surfaces cross-domain relationships (e.g., power ripple coupling into ADC offset coupling into clock cascade). Root-cause hypotheses are ranked by confidence score with affected component attribution and resolution suggestions.
  • Firmware Diff & Incident Replay Binary-level, register-aware comparison between running and baseline firmware versions. Simulation lab for injecting hypothesised fault conditions and validating root causes against historical field data before committing to a fix.
  • Knowledge Base Searchable, article-structured repository of resolved incident findings — root cause, resolution steps, affected device families, firmware versions, and signal tags. Articles are generated from and linked to specific incidents, making institutional knowledge findable and reusable across all future investigations.
  • Engineer Onboarding Guided, stage-gated learning path covering platform architecture, hardware setup, drift workflows, and CI/CD gating. Designed to reduce time-to-independent-investigation from weeks to days.
  • CLI & API-First Architecture A 17-command standalone CLI (diagiot) enables fleet management from any terminal, IDE, or CI pipeline. A 31-endpoint REST API and WebSocket event stream expose all platform data to external tools and custom dashboards.

Architecture Summary

The DiagIoT MVP is implemented as a Node.js + Express backend with an in-process event-driven store (no external database required), a WebSocket push layer for live UI updates, and a single-page frontend with 10 screens. All three agents run as logic modules within the server process. The system is deployable from a single npm start command with zero external dependencies at the infrastructure level.

Outcome: DiagIoT moves embedded fleet management from reactive manual investigation to a proactive, automated, agent-driven closed loop — catching firmware drift risk before it ships, detecting field anomalies within seconds of threshold crossing, and preserving the institutional knowledge that makes every future investigation faster than the last.
