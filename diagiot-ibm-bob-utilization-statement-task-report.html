Written Utilization Statement

How IBM Bob Was Used

Phase 1 — System Design and Scope Definition (Plan Mode)

The project began with a full technical specification document (DiagIoT_System_Technical_Summary.docx) describing a multi-week, multi-agent platform build. Bob was engaged in Plan mode to read and analyse the spec, assess the team's timeline constraints (a three-person team, two-day weekend sprint), and produce a realistic execution plan that correctly separated what was buildable from what should be deferred.

Bob's planning output — the diagiot-mvp-sprint-plan.md — explicitly identified seven dependency-ordered sub-tasks, audited the existing codebase state against the spec, and named the components that should be polished static mocks rather than live logic. This planning document prevented the team from over-investing in features — such as the 6×6 real-time correlation matrix, the multi-hypothesis ranking engine, and the incident replay simulation engine — that would not improve the demo but would consume the entire build window.

Phase 2 — Scope Guardrail Authoring (Agent Mode)

Bob authored the AGENTS.md file at the repository root, establishing a machine-readable and human-readable contract that governed every subsequent Bob session. The file contained:

From AGENTS.md (Bob-authored, active in every session):

"Bob agent guardrail: This file defines the MVP scope for this repository. Do not implement anything not listed in the MVP scope table below. If a feature is not in scope, add it to the 'future work' list — do not build it."

The file defined the MVP scope table (20 components with Real/Mock status), entity JSON schemas for Device, Alert, Scan, and KnowledgeArticle, the drift score formulae, threshold tables, and the three agent implementation locations.

This guardrail was active in every subsequent Bob session — any request that would have added database persistence, microservice splits, GitLab integrations, or live correlation matrix computation was deflected by this file, keeping all agent-generated work within the agreed sprint boundary.

Phase 3 — Full-Stack Implementation (Agent Mode)

With the scope defined and guardrail active, Bob implemented every major code artifact in the repository. In each task, Bob first read the relevant existing files — routes, store methods, seed data shapes — before writing any code, ensuring new code worked against actual implemented interfaces rather than assumed ones. The engineering discipline applied was minimal change: produce the least code that satisfies the requirement, no added abstractions, no speculative error handling.

Key implementation sessions covered:

  • Express + WebSocket server with JWT guard and integration startup
  • In-process data store (EventEmitter + Maps — no database)
  • Drift Engine: computePreShipScore() and evaluateTelemetry() with threshold-crossing debounce
  • 31-endpoint REST API across fleet, alerts, scans, baselines, agents, integrations, knowledge, incidents, and system routes
  • All 6 integration adapters: GitHub (HMAC-SHA256 webhook), Arduino (serial + upload), Jenkins (polling), Docker (daemon events), Keil/STM32 (multipart ELF upload), VS Code (WebSocket build hook)
  • 17-command CLI with REPL mode and ANSI-formatted output
  • WebSocket data layer (app-data.js): window.D store, reconnect logic, all event handlers, helper functions
  • Screen router (switchScreen, softRefreshScreen) and all 10 frontend screens

Phase 4 — Documentation Authoring (Agent Mode + Ask Mode)

Bob authored all four core project documents: the root README.md (architecture diagram, quick start, integration setup guides, API reference), docs/README.md (system overview, agent descriptions, screen inventory, design token reference), docs/HANDOFF.md (install steps, env vars, seed data, demo flow, troubleshooting), and docs/plans/api-contract-mvp.md (complete REST + WebSocket contract with request/response shapes). Ask mode was used during documentation to verify that schema descriptions matched what was actually implemented in the store and routes.

Key principle applied throughout: Bob was instructed to investigate before answering — every code question required reading the relevant file before responding. No claims were made about API shapes, store methods, or route behaviour without first inspecting the actual source. This grounded-only approach prevented hallucinated interfaces and ensured all generated code integrated correctly on first attempt.

Scope Management

Out-of-Scope Items Deflected by Bob Guardrail

The following features were explicitly identified by Bob during planning as out of scope for the MVP sprint and recorded in AGENTS.md. None of these were implemented. Their exclusion was enforced by the project-scoped guardrail active in every Bob session.

  • Separate agents/pre-ship/, agents/monitor/, agents/onboarding/ microservices — all agent logic embedded in src/server/
  • Persistent database (SQLite, Postgres, etc.) — in-process store sufficient for MVP scale
  • Real-time 6×6 signal correlation matrix computation — hardcoded illustrative heatmap in Drift Analysis screen
  • Multi-hypothesis ranking engine — single pre-populated hypothesis card per device
  • Incident replay simulation engine — pre-populated "confirmed" result in Reproduce Incident screen
  • Onboarding Agent live knowledge curation logic — static Knowledge Base articles from seed
  • Firmware Store service — firmware artifacts referenced by version string only
  • GitLab or SEGGER Ozone integrations — documented as "Planned" in integration matrix
  • Any new REST API endpoints beyond the 31 already implemented
  • Authentication enforcement — JWT guard optional by design, disabled by default
